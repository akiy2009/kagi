# セキュリティポリシー

Kagi Identity はセキュリティに敏感な認証・Identity Provider です。悪用可能な脆弱性を公開 Issue や Pull Request へ書かないでください。

## 脆弱性の報告

1. 可能であれば GitHub の **Private vulnerability reporting** を使用してください。
2. 非公開報告が利用できない場合は、メンテナーの GitHub プロフィール経由で連絡し、安全な開示チャネルを依頼してください。
3. 影響を受けるコミット / バージョン、影響、前提条件、安全な範囲での最小再現手順を含めてください。
4. 実際のユーザーデータ、本番資格情報、秘密鍵、認可コード、アクセス / リフレッシュトークン、セッション Cookie を含めないでください。

トリアージと協調的な修正の時間を確保してください。メンテナーが確認するまで、報告は受理されたとはみなされません。

## デプロイ要件

ローカル評価以外へデプロイする前に、[デプロイガイド](DEPLOYMENT.md) と [設定リファレンス](CONFIGURATION.md) を確認してください。最低限、次を実施します。

- HTTPS を使い、Issuer、ブラウザーオリジン、WebAuthn RP ID を整合させる。
- 本番ではデモクライアント登録を無効にし、アカウント登録ポリシーを意図的に決める。
- 管理トークンと登録トークンを秘密管理領域に保存し、漏洩が疑われる場合はローテーションする。
- Rust 依存関係を最新に保ち、自動依存更新をレビューしてからデプロイする。
- エッジ / WAF のリクエスト制限とボディサイズ制限を有効にする。アプリケーションは PostgreSQL の原子的レート制限カウンタを使うため、信頼済みプロキシと正確な `KAGI_CORS_ORIGINS` 許可リストを設定する。
- データベースアクセス、署名鍵、バックアップ、リストア資格情報を保護し、復旧手順を演習する。
- トークン、認可コード、セッション識別子、資格情報素材をログに出さない。
- 独立したセキュリティレビューと、対象プロファイルに沿った OAuth / OIDC / FAPI 適合テストを実施する。

## 実装されている主な防御

| 領域 | 防御 |
| --- | --- |
| 認可リクエスト | redirect URI の完全一致、PKCE S256 必須、`state` / `nonce` の受け渡し、RFC 9207 の `iss` |
| 同意フロー | CSRF トークン、Origin + `Sec-Fetch-Site` 検証、フローの原子的 compare-and-swap による二重コード発行防止 |
| 認証 | WebAuthn の challenge / origin / RP ID / UP / UV 検証、署名カウンタによるクローン検出、最後のパスキー削除禁止 |
| セッション | 不透明なセッション ID の SHA-256 保存、HttpOnly + SameSite=Lax、HTTPS では `__Host-` プレフィックス、絶対・アイドル期限 |
| トークン | ES256 署名、`typ: at+jwt`、短命アクセストークン、リフレッシュローテーションと再利用検出、保存時 SHA-256 |
| DPoP | `typ=dpop+jwt`、`htm` / `htu` / `iat` / `jti` 検証、リプレイキャッシュ、コード発行時の `dpop_jkt` 束縛 |
| 失効 | 署名・issuer・期限・DB 状態を検証してから `/revoke` を適用、セッション / 同意取消時のトークン失効 |
| クライアント登録 | HTTPS / 実ループバック限定の redirect URI 検証、秘密 JWK 拒否、`jwks_uri` 拒否、サイズ・名前制限 |
| ブラウザー | CSP（`form_post` は nonce + `form-action` を RP オリジンに限定）、HSTS、COOP / CORP、Permissions-Policy、クリックジャッキング防止 |
| エラー | 内部 DB / 署名 / WebAuthn エラーの詳細はサーバーログのみ。クライアントには汎用エラーを返す |
| 可用性 | 共有レート制限、リクエストサイズ制限、`/readyz` による DB 検査 |

## 既知の制約

- 正式な OAuth / OIDC / WebAuthn / FAPI 認証は取得していません。
- 一部のプロセス内キャッシュ（署名鍵など）は単一ノード前提です。
- バックチャネルログアウトの配信はベストエフォートです。本番では HTTPS のみを許可し、プライベート / リンクローカル宛先、リダイレクト、URL 内の資格情報を拒否します。ループバック HTTP は開発時のみ許可されます。
- CIBA と SD-JWT VC は未実装です。
- 署名鍵はデータベースに保存されるため、バックアップに鍵素材が含まれます。
- 本番の高保証用途では、外部 KMS / HSM、独立監査、対象プロファイルの適合テストが必要です。

## 認証ステータス

本プロジェクトは、OAuth、OpenID Connect、WebAuthn、FAPI の正式な認証を**主張しません**。ユニットテスト、統合テスト、CI ワークフローの成功は認証ではなく、それ自体が本番運用の準備完了を示す証拠でもありません。
